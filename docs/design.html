Moot Plugin Design

A standalone Claude Code plugin for bigger engineering tasks. Debate the design first with a multi-model council, then ship it as small stacked PRs, with every step visible to the human.

TL;DR

  • One idea: no code before the council, the spec, and the plan have each passed a human GO. Then one GO per PR.
  • Council runs up to five rounds: proposals, swap and judge, then contested points only. Output is one verdict file with a TL;DR on top.
  • Roles, not models. Eight roles in one editable table decide which runner and model do what. Agents never talk to each other, only to the lead.
  • One state file per piece of work drives the handoff, the dashboard, the links, and the context warning.
  • Review pages for verdict, spec, and plan: Artifact page plus local HTML, TL;DR first, tests collapsed, no diagrams that need decoding.
  • Generic by design. Nothing company specific. Repo facts live in a repo profile written at setup and kept fresh by the review stage.
  • Codex is optional. Runs headless, shown live in a tmux pane through codex resume. A Claude-only council works out of the box.

Scope

Moot does

  • Take an epic as tickets, a PRD, or a description with designs.
  • Run council, spec, plan with human gates and review pages.
  • Split the work into tickets and small stacked PRs.
  • Run each PR through brief, implement, verify, review, evidence, draft PR.
  • Keep state, handoffs, gotchas, and a dashboard pane.
  • Quick mode for a single ticket or fix, same stages, no council.

Moot does not

  • Run unattended. No autonomous mode, no board.
  • Merge. The human merges; an optional merge skill helps with triage and chain rebase.
  • Know your repo. Build, test, run, and screenshot commands come from the repo profile.
  • Define test style. Only the TDD loop and the gates are generic.
  • Ship a status line. The dashboard is a mod pane.

Lifecycle and gates

Full ceremony, for an epic:

Intake→ Factpack→ Council ×1–5→ GO 1→ Spec + judge→ GO 2→ Plan + judge→ GO 3→ Tickets

Then for each PR in plan order:

GO→ Brief→ Implement→ Verify→ Review #n + fixes→ Evidence→ Draft PR

Light ceremony, for a single ticket or fix (/moot:task): research brief by legwork, a one-page plan by the lead, one GO, then the same per-PR stages. No council, no spec.

  • Intake collects everything a human would look at into assets/: PRD, design exports, screenshots, linked tickets. If a design tool is connected, frames are exported there. The plugin has no Figma dependency.
  • Factpack is a legwork pass over the repo and the assets: what exists, where, which flags, which screens. Every council member gets it, so they argue about the design, not about the facts.
  • Tickets are created after GO 3, one per PR, always as local records: the tasks list in state.json plus a tasks/<ID>/ folder each. The tracker setting only decides whether that list is mirrored outward.
    When the epic already has tickets: intake fetches all of them into assets/, so the factpack, the council and the spec treat them as constraints, not as the plan. The plan is still cut by PR size. At GO 3 each PR is mapped to one existing ticket, or marked new. One ticket that needs several PRs keeps its id with a branch suffix (PROJ-124-a, -b), and gets one PR link per PR. The plan judge checks the mapping both ways: every existing ticket is covered by a PR or listed as dropped with a reason, and leftovers are shown to the human at GO 3. The lead never closes or edits a ticket it did not create. If the tickets are already PR-sized, the plan adopts them one to one.
  • GO is literal. The lead asks "GO for PR 2?" and waits. "Looks fine" or "let's continue" is not a GO. A config switch lets an epic run the whole chain after GO 3 instead.
  • Stops happen only on a failed verify, a blocking review after two fix rounds, or an agent that needs the human.

Council

Members are the rows with the council role in the roles table. Each member gets the same brief: the question, the factpack, the assets folder, the report contract. Members must go through every asset and list what they see before they propose.

RoundInputOutput per member
1 ProposalsBrief, factpack, assetsOne recommended design, rejected alternatives with reasons, file references, asset observations
2 Swap and judgeAll other proposals, verbatimAgreed · Contested (each point with both positions) · Revised proposal
3 to 5 Contested onlyOnly the open points, both positionsPick a side or propose a third option, with evidence

Stop rule. The loop ends when the contested list is empty, when a round changes nothing, or after three contested rounds. Whatever is left, the lead decides with written reasoning and marks "lead-decided" so the human can override it.

Verdict file. council/verdict.md: TL;DR, the one design, settled points, lead-decided points, rejected alternatives, risks, a coarse work split, who argued what. The human's override box is prepended on top. The verdict is the only thing the council produces, and it is the input to the spec.

Codex members run headless and keep their session across rounds through codex exec resume. Claude members are subagents resumed by name. A member that dies is dropped and reported; with one member left the council degrades to a deep brainstorm and says so. Without codex the default is exactly that: one Claude member at high effort running the deep brainstorm, not two Claude members on different models.

Roles and routing

One markdown table in .moot/roles.md, edited by hand. The lead reads it before every spawn and passes the model explicitly. Values below are example defaults that setup fills in.

RoleDoesNeverRunner · model · effort
leadThe session. Frames, spawns, merges verdicts, writes spec and plan, commits, keeps stateBig implementation workthe session itself
councilProposes and argues design, read-onlyEdit filesclaude fable · high; codex gpt · high
judgeScores a spec or plan against criteria, pass or fail with findingsWrite the thing it judgesclaude fable · high
executorImplements one PR in the worktree, code and tests, reports to a fileOpen PRs, message other agentsclaude opus · xhigh
reviewerReviews the diff before the PR, compares to design, writes the test keep/merge/delete listFix codeclaude fable · high
qaRuns the app, before and after captures, compares to designJudge designclaude opus · high

Advisor routing. An agent that needs help writes the question in its report and stops. The lead asks the advisor, then sends the answer back. Agents never message each other; that line is in every charter.

Banned models are a separate list in the same file. The lead refuses to spawn them even if asked.

State file

One state.json per piece of work. The lead is the only writer and writes it with the Write or Edit tool, so the dashboard can re-read it the moment it changes. Everything else is derived from it.

Task stages

Default stages for one PR, in order. The lead appends dynamic ones as they happen.

StageWhoDone when
GOhumanA literal GO for this PR
briefleadbrief.md written: scope, files, test behaviors, repo rules that apply, the "write your report to this file" line
implementexecutorReport written, diff present in the worktree branch

review #nreviewerFindings file with a test keep/merge/delete list; "clean" or "blocking"
fixes after review #nexecutorOnly when blocking; fixes are committed, then review #n+1. Two rounds max before the lead stops and asks
evidenceqaBefore and after captures when the repo profile has a capture command and the PR touches UI; design, before and after side by side, deltas written against the design; report.html. The reviewer gets the report link, not the images
draft PRleadStacked on the previous branch, body from the template, evidence report linked, state and links updated

Review pages

Verdict, spec, and plan each exist twice: the markdown the agents work on, and a page a human can read in two minutes.

  • TL;DR first. Every page starts with a short block: what, why, what changed since the last version, what needs a decision.
  • Structure the renderer understands. Fixed section names in the markdown template. Sections named Tests collapse by default. Decisions and open questions get their own blocks. Relations and flows are tables and cards, never diagrams that need decoding.
  • Where it lives. render-page.sh turns the markdown into a local HTML file next to it. The lead publishes the same page with the Artifact tool and stores the URL in the links list. Comments reach the lead only when the reviewer sends them to Claude on the page, and only while the session that published the page is alive; a new session re-watches the page from the links list and reads the rest on request.
  • Judges read the markdown, humans read the page. Same content, two surfaces.
  • The plan page is a PR list. The primary view is the ordered list of PRs, one row each with branch, base, scope, and ticket (an existing id or "new"). A row expands to its files, behaviours to test, and the brief. The long form stays in plan.md for the judge and the executor.

This document is the first page of that kind. If it reads well, the template is the shape of this page.

Handoffs and session hygiene

  • A handoff is written at session end and whenever the lead crosses the context threshold. Files are timestamped, handoff-YYYY-MM-DD-HHMM.md, newest wins, and the state file points to the latest. Older files are the history, so there is no separate ledger.
  • A handoff starts with "START HERE": the next action, the open GO, the links, then what happened and why.
  • The session start hook finds the latest handoff for the current work and injects its top section plus the GO rule.
  • The lead shuts down every agent it will not message again, right after reading its report. The dashboard lists agents that finished but are still alive.
  • Every agent writes its result to a file and replies "written + N lines". The lead reads the file, never the message.
  • Context threshold is a number in config. The mod warns at that point and the lead writes a handoff and suggests a fresh session. This is the primary stop: the lead should finish on the alert, not run into compaction.
  • Fallback for compaction: when compaction is about to happen before the alert was acted on, the PreCompact hook blocks it once and shows you "ask the lead for a handoff first". The hook cannot talk to the model, so you relay it. The second attempt goes through. Compaction is never the normal path.

Repo profile

Setup spawns a legwork agent that inspects the repo and writes .moot/repo.md. The human reviews it once. It holds:

  • install, build, test, type check, lint, codegen commands, and what must run after a checkout or rebase
  • how to launch the app and how to capture a screenshot of a screen, if the repo can
  • worktree setup command, merge policy (squash or merge), PR template path, ticket prefix, main branch
  • pointers to the repo's own rules: instructions files, test style, skills
  • tracker mirror, if the repo has a connected tracker: the skill or command for create ticket, fetch ticket, attach PR link. When these are found, setup sets tracker to repo; otherwise it stays none

Keeping it fresh: executor and qa reports have a field "profile wrong or incomplete". The lead updates the profile during the verify stage when that field is filled.

Gotchas

One file per topic under .moot/gotchas/ and an index with one line per file. The session start hook loads the index only. Each stage names the topics it needs: the merge skill loads the git topic, the executor brief includes the topics for the files it touches. A gotcha is appended the moment something bites, by the lead, in the same session.

Agents and runners

An agent file is a charter the lead spawns with one line. It carries the role's job, its hard limits as a tools list, the report contract, and model: inherit. The lead passes the model from the roles table. Skills drive the lead through a phase; agents are the workers inside the phase.

AgentCarries
council-memberAsset inspection duty, proposal format, round 2 and contested formats
spec-judge, plan-judgeCriteria lists; plan-judge also checks every requirement maps to a test behavior and that no test code is in the plan
executorTDD loop, red first, planned tests only, no comments policy slot from the repo, "ask through the lead", report format with the profile-feedback field
reviewerReview checklist, compare to design, test keep/merge/delete list, clean or blocking, no manufactured findings
qaLaunch and capture using the profile, compare to design, evidence report
legworkFactpack and inspection formats, read-only
advisorOne question in, one answer out, read-only

Codex runner

codex-run.sh spawns codex headless in the main checkout, read-only sandbox, report through -o, images through -i. It reads the session id from the first event, prints it, and opens a tmux split pane running codex resume <id> so the real codex UI shows the run. A sentinel file marks the end. No custom stream renderer. The pane is a viewer of the saved session, not a live attach: it shows the finished turn in full, and typing into it starts the next turn on the same session. Codex sees its prompt file plus the repo's own AGENTS.md, so the runner puts the agent charter and any named skill text at the top of the prompt. Later rounds use codex exec resume <id>, which takes the sandbox as -c sandbox_mode=…, not -s.

Spawn-time rule for Claude agents: the lead sets the model explicitly on every spawn. Omitting it inherits the session model, which is the expensive one.

Tests

The plugin carries only the discipline, never the style. Style belongs to the repo and is read from its own rules.

  • Plan gate. The plan lists test behaviors, one line each. The plan judge rejects any line that cannot name the production change that would make it fail. No test code in plans.
  • Executor loop. Red first: write the test, run it, see it fail, then implement. Only planned tests, plus temporary ones deleted before the PR.
  • Reviewer list. Keep, merge, or delete for every test in the diff, with the breaking change named for each keep. Delete is a normal outcome.
  • Two numbers in the PR body. Tests added versus deleted, and test lines versus production lines. A signal, not a rule.

Worktrees

One worktree per piece of work, created with Claude Code's built-in worktree support: it lives at <repo>/.claude/worktrees/<name> on branch worktree-<name>, cut from the remote default branch. The repo profile's setup command runs inside it after creation. Stacked branches are created with git inside the same worktree, and the worktree stays open until the whole stack is merged, since reusing a name whose branch was merged resets it. A config switch turns worktrees off for repos where they do not work.

Working files stay in the main checkout, written through scripts. A session inside a built-in worktree cannot use Write or Edit on a path in the main checkout, but Bash and Read work there (verified 2026-10-20). So every write under .moot/ goes through a plugin script run with Bash: moot-state.sh merges fields into state.json, moot-note.sh appends a handoff or a gotcha. Reads use Read with the absolute path from the repo root. The dashboard reloads when it sees a Bash call that names .moot/, plus a slow timer.

Dashboard mod

A pane beside the transcript, opened with /moot:dash. It reads the state file and redraws when the lead's state script runs; a slow timer covers codex-side changes. Shape borrowed from the flightdeck mod, cut to about a third of its size.

Shows

  • Work id and title, ceremony, phase
  • Council: in progress round N, or done; spec and plan with judge rounds; which gates passed
  • Current task: the stage list as a checklist, dynamic rows included
  • Agents: lead with context percent; every other agent with role, status, context where known; finished ones kept
  • Links: every entry in the links list
  • A warning line when the lead's context crosses the threshold

Does not

  • Attach to or open agent panes
  • Show cost, permissions, or tool logs
  • Replace the status line
  • Run anything

Per-agent context for Claude subagents comes only from turn events, so the mod must be loaded from session start. Codex context is not available and shows as n/a. The mod's own memory is cleared on resume, clear and branch, so it re-reads the state file on every session start. The state file path is absolute, from the repo root, so a session inside a worktree still finds it.

Setup and config

/moot:setup creates .moot/, writes the roles table with defaults, asks the ignore question, checks tools (gh required, codex and tmux optional), runs the repo inspection, and ends with the profile open for review.

config.json is written once by setup: defaults plus what the inspection found (main branch, merge policy, ticket prefix come from the profile). After that you edit it by hand, like roles.md. Every skill reads it at start; nothing in the flow writes it back. Runtime values live in state.json.

Example config.json and what each key affects 
{
  "tracker": "none",                 // none | github | repo
  "ticketPrefix": "PROJ",
  "mainBranch": "main",
  "merge": "squash",                 // squash | merge, from the repo profile
  "goPerPr": true,
  "worktree": { "enabled": true, "setup": "npm ci" },
  "council": { "maxContestedRounds": 3 },
  "contextWarnTokens": 350000,
  "pages": "artifact",               // artifact | local
  "evidence": { "capture": "" }      // repo command: <route> <out.png>; empty = skip captures
}
KeyAffects
trackerThe local tasks record always exists. This key decides whether it is mirrored outward and where ids come from. none: no mirror, ids minted from ticketPrefix. github: each task mirrored as a gh issue. repo: mirrored through the commands or skill the repo profile names (for example a connected Jira CLI). The mirror is three operations: create a task and record the external id back into state.json, fetch an existing ticket into assets/ at intake, attach the PR link after the draft PR. When mirrored, the external id becomes the task id, so branches and folders match the tracker. If the mirror fails, the local record stays the truth and the lead reports it instead of stopping. Moot carries no tracker client of its own.
ticketPrefix, mainBranchIds of new tasks when there is no mirror, and the base branch of the first PR in a stack.
mergeHow the merge skill and chain-rebase.sh treat a merged parent (squash vs merge commit).
goPerPrtrue: the lead asks GO before every PR. false: one GO at GO 3 runs the whole chain, stopping only on a failed verify, a blocking review after two fix rounds, or an agent asking for the human.
worktreeWhether the epic gets its own worktree, and the command run inside it after creation.
council.maxContestedRoundsThe stop rule for contested rounds 3 to 5.
contextWarnTokensWhen the dashboard warns and the lead writes a handoff. Copied into state.json so the mod reads one file.
pagesartifact: publish spec and plan pages with the Artifact tool and store the URL in links. local: HTML file only.
evidence.captureThe before and after step in qa. Empty means captures are skipped and qa only compares to the design.

Build order

  1. This design page, reviewed and verified done 2026-10-20: one codex and one Claude red-team pass over the tool claims, plus three spikes (dashboard mod, PreCompact hook, worktree isolation). Findings are folded into the sections above.
  2. Setup and repo profile
  3. State file, handoffs, session start hook
  4. Council skill, council-member charter, codex runner
  5. Spec and plan skills, judges, page renderer, Artifact publish
  6. Task loop: brief, executor, verify, reviewer, qa, draft PR
  7. Dashboard mod
  8. Merge skill, optional

Dogfood on the next real epic under full ceremony before polishing. Quick mode and the mod mature on that run.
